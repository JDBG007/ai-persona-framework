# 信箱协议

> **一个目录，一套命名，一条方向。**
> 越是跟「重要的人」通信，协议越要简单到不会记错。

---

## 一、形状：一个目录，两个前缀

```
信箱/
  in-<序号>-<品类>-<标题>-<日期>.md     ← 进来的 / 我投出去的？
  out-<序号>-<品类>-<标题>-<日期>.md    ←
  README.md                             ← 协议本身就在这儿
```

**关键：文件名自带方向、序号、品类、日期。**

**为什么不在文件内容里写这些**：
因为**看文件名就能分类**，不用打开十个文件猜哪个是哪个。
（一个目录里超过三十封信之后，这一条会救你很多次。）

---

## 二、协议要写在哪

**协议本身必须住在信箱目录里**，不能住在别处。

**理由**：谁来这个目录，第一眼就该看见规矩。
写在别处的协议，等于**写给不会去看的人**。

---

## 三、一封信的最小结构

```
要什么：求助 / 请裁 —— <一句话>

一、卡在哪      <具体障碍，我试过什么>
二、要你判什么   <一个问题，最好只有一个>
三、来路         <谁说的、什么场景>

（可选）附：<需要他看的文件 / 数据>
```

**只有三节。**

理由：**收信的人不是在读文章，是在做判断。**
每一节都在帮他把判断做完，不是在展示你做了多少。

---

## 四、为什么「一封信一个问题」

因为**对方的判断成本是线性的**。

一封信里塞五个问题，他会：
- 挑最简单的答（其他被忽略）
- 或者全部答一遍但每个都很浅
- 或者干脆不答（信太长了）

**一封信一个问题**，才有机会得到真判断。

> 需要问五个 → **写五封，或者先自己解决三个。**

---

## 五、回信与存档

| 动作 | 规矩 |
| :-- | :-- |
| **回信** | 同目录，换前缀，序号接上 |
| **存档** | 结案的信不删，移到存档子目录，**原位留三行指针**（去向 / 日期 / 关键词） |
| **禁止** | 直接删、原地改名（会让对方的引用断掉） |

---

## 六、一条软性但重要的规矩

> **信里的语气，按关系来。**
> 对老师用敬语；对家人直接说；对陌生人清楚简短。

**这不是客套，是效率**：
同一句话，用错语气，对方会先处理情绪，再处理内容。

---

## 七、这一层的验收

1. **新人（或新会话的她）进这个目录，五分钟内能不能看懂怎么用？** ← 主判据
2. **信的顺序还有效吗？** 序号有没有重复或跳号
3. **存档有没有留指针？** 指向断了的，等于删了
