# 三条红线（放原文）

> **这一份是「原文级」的** —— 不写成指针，不缩写成「详见某某」。
> **理由**：最危险的规矩，不能依赖「记得去翻」。翻不到就是没有。

---

## 红线一：往「可能已有内容」的目标写东西 → 先清空 ＋ 写完逐字读回

**为什么**：
追加写、合并写、编码转换、行尾转换 —— 这四件事**每一个都可能静默地毁掉原文**。
而且毁掉之后，**文件看起来还在、还能打开**。

**正确做法**：
```
① 先快照（复制一份带时刻的备份）
② 清空 / 明确声明覆盖
③ 写
④ 读回，逐字（字节级）校验
```

---

## 红线二：判断「存在 / 成功」→ 读那个对象本身，不信工具返回值

**为什么**：
- `Test-Path` 测不出**断链**
- 脚本 exit 0 可能是**它根本没干那件事**
- 界面上显示成功，可能只是**界面刷新了**

**正确做法**：
```
想知道它存在？→ 读它的字节 / inode / 内容
想知道它成功？→ 读目标对象，比对预期
```

> **一句话**：**工具自报的成功不算完成；独立读回目标对象才算。**

---

## 红线三：动窗口 → 不许改大小或最大化状态

**为什么**：
窗口尺寸会改变**坐标**，而坐标是很多自动化的地基。
一改，所有写死的坐标全废，而且**废得很隐蔽**（点偏一点，看起来还是点了）。

**正确做法**：
```
允许：拉前台 / 切标签 / 移动
禁止：改尺寸 / 最大化 / 最小化还原
需要尺寸变化 → 先问，别自己动
```

---

## 这三条的共同点

它们都是「**错误不会立刻显形**」的那种。

| 红线 | 错了之后的样子 |
| :-- | :-- |
| 一 | 文件还在，内容已经毁了 |
| 二 | 一切正常，只是没做 |
| 三 | 还能点，只是点偏了 |

> **这比直接崩掉难一万倍。** 崩掉你知道要修；**静默失败**你会带着它继续干活。

**所以这三条放在最外层，且放原文。**

---

## 一条配套的元规矩

> **同一个办法失败两次 → 停手数家当。**
> 说明是这条路不对，不是参数不对。

人（和 AI）的本能是：第一次失败，调参数；第二次失败，再调参数。
**但连续两次同一个位置失败，通常意味着整个方法错了。**

停下来，数一数：手上到底有什么、缺什么、这条路本来通不通。
