# 只信读回 ｜ 不信自报

> **这是整个框架的信任地基。**
> **一句**：**工具自报的成功不算完成；独立读回目标对象才算。**

---

## 一、它要治的病

AI 干活时最典型的失败，不是「做错了」，是**「以为自己做了」**。

| 症状 | 真相 |
| :-- | :-- |
| 「已经把文件写好了」 | 写到了另一个路径 / 被编码毁了 / 根本没写 |
| 「脚本跑通了，exit 0」 | 它跑到一半静默退出，什么都没做 |
| 「页面已经填好并发送了」 | DOM 里有字，编辑器模型里是空的 |
| 「测试全部通过」 | 测试根本没被收集到（0 个测试 = 0 个失败） |

**共同点：错误不会立刻显形。**
所以必须有一个动作，**去读那个对象本身**。

---

## 二、三层不信

### 2.1 不信工具

工具的返回值是**它的说法**，不是**事实**。

```
✗ if (命令成功) { 认为文件写好了 }
✓ 命令(); 读出文件字节; 与预期比对; 才算
```

### 2.2 不信别人

任何反馈都是**转述**。
转述会丢细节、会加理解、会好心地说「应该没问题」。

### 2.3 不信下一轮的自己（★ 最难的一条）

因为她会**记住一个合理的版本**。

- 当时：脚本报了个奇怪的错，她绕过去了
- 一小时后：「那个问题我解决了」
- 一天后：「那个问题本来就不存在」

**这不是撒谎，这是记忆的正常加工。**

所以：**结论必须是读回来的，不能是回想起来的。**

> 说得更狠一点：**「我记得我验过了」不构成验证。**

---

## 三、怎么读回才算数

读回要满足三个条件：

| 条件 | 意思 |
| :-- | :-- |
| **读的是目标本身** | 不是读缓存、不是读配置、不是读日志 |
| **比的是字节 / 结构** | 不是「看起来对」 |
| **能复现** | 换一次跑，同样的方式还能验一遍 |

### 一个反例

> 写完一个文件，用**同一个编辑器**打开看一眼，觉得内容对。
> —— 这不算读回。因为编辑器可能给你的是它**内存里的版本**。

**算数的读法**：重新从磁盘读字节，和预期逐字比。

---

## 四、这条规矩衍生出的几条具体纪律

| 纪律 | 来源 |
| :-- | :-- |
| **写完必须读回** | 写不一定成功 |
| **测「存在」要读 inode / 内容** | `Test-Path` 测不出断链 |
| **测「成功」要读产物** | 退出码只是"它说它成功了" |
| **改 A 就查 B** | 一处路径改了，全盘引用都要扫 |
| **数是量出来的，不是估的** | 不确定就写「未量」，不填估的 |

---

## 五、它的代价（诚实地讲）

**慢。**

读回比写完慢，比完比跑完慢。
而且大部分时候，工具**真的成功了** —— 那这些读回看起来全是浪费。

**为什么还是值得**：

因为一次静默失败的成本，远远高于一百次多余的读回。
而且更贵的是**信任成本**：一旦你发现自己说过「做完了」而其实没做，
**你说的每一句话都要被重新验一遍。**

> **判据**：**这次验证的成本，比这次做错的成本低吗？**
> 绝大多数时候，是。
