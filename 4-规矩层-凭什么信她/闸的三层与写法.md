# 闸的三层与写法

---

## 一、先问：这道闸该不该存在

不是所有规矩都值得做成闸。**闸是有成本的**：

- 每次跑都要时间
- 输出会占上下文
- 太吵会被绕过

**所以每加一道闸，要回答两个问题：**

1. **它拦下来的是「再也回不去」的事吗？**
2. **它会不会让正常干活变得很烦？**

两个都是「是」→ 放硬停层。
第一个「是」第二个「否」→ 流程层。
第一个「否」→ **根本不该做闸**，写进经验就好。

---

## 二、三层结构

### 2.1 流程层（最常用）

**做什么**：在固定时刻，按顺序跑一串检查。

| 时刻 | 例子 |
| :-- | :-- |
| **开工** | 读骨 / 读状态件 / 查信箱 / 报欠账 |
| **写文件前** | 查 BOM / 查语法 / 查路径 |
| **收工** | 扫一遍「我说过要做的事，真做了吗」 |

**特点**：
- 黄灯为主，不拦人
- 但**确实会被跑到**（因为挂在固定流程上，不靠自觉）

### 2.2 硬停层（最少，但最硬）

**只给不可逆**：删除、覆盖、发信、对外发送、动别人的东西。

**特点**：
- 红灯，`exit ≠ 0`
- 通常会要求人批准
- 有「留痕放行」通道：明知要动红线时，命令里显式写一个标记 ⇒ 放行但记账

> **为什么要有「留痕放行」**：
> 因为绝对禁止的结果，是**人会去找更野的路绕过去**。
> 给它一个正门：**你可以在明知故犯的时候，留一个字说自己知道。**

### 2.3 记忆层（事后核对）

**做什么**：算一遍、比一遍、记一笔。

例：字节数对不对、sha 一不一致、账目平不平、自证串能不能复算。

**特点**：
- 不拦人，但**结果会进入下一轮的视野**
- 是「她凭什么敢说这事做完了」的唯一依据

## 三、写一道闸的最小骨架

```
输入：要检查的对象（路径 / 行为 / 文本）
  ↓
读对象本身（不是读缓存、不是读配置说的）
  ↓
比对预期
  ↓
三档输出：
   0 = 通过（连"我通过了"都不用多说）
   1 = 黄灯（提醒，但别废话）
   2 = 红灯（说清哪一处、期望什么、实际什么）
```

### 三条写法纪律

1. **说清「期望 vs 实际」** —— 只说「失败」等于没说
2. **给退出码** —— 文本会被人忽略，退出码不会
3. **引用出处** —— 报错时带上「这条判据来自哪」，不然半年后没人知道为什么

---

## 四、闸自己的验收（★ 最容易被跳过）

> **没有跑过的闸，只是文档。**

每道闸要有一个「故意弄坏」的测试：

| 测试 | 期望 |
| :-- | :-- |
| 故意改成错的 | 必须红 |
| 故意删掉一段 | 必须红 |
| 正常情况 | 必须绿，且**安静** |
| 只差一点点（边界） | 行为要明确，不能「看情况」 |

**特别关注最后一条**：边界含糊的闸，会在某一天开始**随机红或随机绿** ——
那时你会开始不信它，然后把它关掉。

---

## 五、一条长期经验

**闸的数量不该无限增长。**

当闸多到每次开工要跑十几道、打印几百行时，
她**不会更安全，只会更习惯忽略**。

**健康的样子**：
- 流程层：几条，短，必过
- 硬停层：极少
- 记忆层：默默算，只在不对时说话

> **判据**：**这道闸上一次响，是什么时候？**
> 如果它从来不响，可能它没用；如果它一直响，可能它在骗人。
